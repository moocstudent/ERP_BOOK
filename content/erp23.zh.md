## 核心讲义

### 数据迁移:上线成败的隐形主战场

新系统配置得再好,数据搬不进去或搬错了,上线即瘫痪。迁移对象分三类,难度递增:

1. **主数据**:物料、客商、BOM、科目、价格——量大但结构清晰;
2. **期初余额**:库存数量与金额、应收应付未清项、总账余额、固定资产净值——必须与旧系统**对账到分**;
3. **未清单据**:未完成的采购订单、在产工单、未发货销售订单——最麻烦,要在新系统里「重建现场」。

历史单据(三年前的发票)通常**不迁移**——归档旧系统只读保留,新系统轻装上阵。

### 迁移循环:清洗 → 映射 → 试跑 → 核对

**清洗(cleansing)**是最被低估的工作:十年老系统里,30% 的物料早已停用、客户重复建了三遍、提前期字段一半是空的。原则:**垃圾不迁移**——迁移是给主数据「大扫除」的唯一机会,错过再无。

**映射(mapping)**:旧字段 → 新字段的翻译表。旧系统「客户等级 A/B/C」→ 新系统「客户组 01/02/03」;旧编码 → 新编码规则。映射表本身要业务部门签字——它是迁移的「合同」。

**试迁移(trial load)**至少两轮:第一轮暴露格式问题,第二轮验证速度与完整性;**终演(dress rehearsal)**按切换时刻表全流程掐秒表跑一遍——切换周末没有第二次机会。

**核对(reconciliation)**要双向:条数对(旧系统 12,480 个物料 → 新系统 12,480)与金额对(库存总值、应收总额、试算平衡逐科目)。核对结果由财务负责人**签字**,这是切换清单上的关键里程碑。

### 集成:上线后的长期战役

ERP 不是孤岛,常年要与周边系统对话。三种集成风格:

| 风格 | 形态 | 适用 |
| --- | --- | --- |
| **点对点** | A 直连 B 的 API | 系统少(≤3 个)时最简单 |
| **中间件/iPaaS** | 统一总线,转换与路由集中 | 系统多,映射复杂 |
| **事件驱动** | 发布/订阅消息队列 | 高并发、异步场景(电商大促)|

点对点系统一多就变「意大利面」:n 个系统两两直连要 n(n−1)/2 条接口,每条都要单独维护。中间件把它变成 n 条——这就是企业买 iPaaS 的数学理由。

**可靠集成的三件保命设计**(沙盘里都出现过):

1. **幂等(idempotency)**:每条消息带唯一键,重发不重复过账——网络重试是常态,不幂等必出重单;
2. **重试队列 + 死信队列**:对方宕机时消息排队等待,超过重试次数进死信人工处理——**消息可以晚到,不能丢**;
3. **监控与对账**:接口日志、每日两边单据数核对——集成断了没人发现,比断了本身更可怕。

### 典型场景速览

- **电商 → ERP**:订单、库存水位双向同步;大促时用消息队列削峰;
- **MES → ERP**:报工、领料回传(ERP 管计划与成本,MES 管排程与工位);
- **银企直联**:付款指令下行、回执与对账单上行(pain.001/pain.002/camt.053 是国际标准报文);
- **EDI**:与大客户/大供应商按行业标准(如汽车业)交换订单、发货通知、发票——「结构化传真」的现代形态。

## 练习

1. 制定迁移范围决策表:物料主数据、五年前已关闭的销售订单、在产工单、上月供应商发票(未付)、员工通讯录——各自迁不迁?为什么?
2. 旧系统库存总值 ¥8,412,300,迁移后新系统 ¥8,398,100。列出三种可能原因与排查方法(提示:估价方法、舍入、漏迁批次)。
3. 设计「电商订单接口」的异常方案:ERP 端物料不存在、客户信用冻结、网络超时三种情况,各自怎么处理?
