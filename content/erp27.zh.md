## 核心讲义

### 两根支柱:最小权限与职责分离

ERP 里「谁能做什么」由两套机制共同约束:

1. **权限 / 授权(authorization)**:登录后菜单里有没有「过发票」按钮——**能不能做**;
2. **审批流(workflow)**:单据保存后要不要经过经理点头——**能不能批**。

只配审批、不配权限:出纳仍可能直接改供应商银行账号。只配权限、不配审批:谁都能建大额 PO。两套都要。

上面再加一条原则——**最小权限(least privilege)**:只给完成岗位工作所必需的事务,不给「以后也许用得着」的全家桶。

### 三层模型:用户 → 角色 → 权限对象

厂商叫法不同,骨架通常是三层:

```
用户(张三) ──赋予──▶ 角色包(采购员 / 仓管员 / …)
                         │
                         └──包含──▶ 权限对象(事务码、公司代码、工厂、金额上限…)
```

设计时按**岗位**做角色包,再赋给具体的人——人走了收回角色即可,不必逐个抠菜单。一人多岗时叠加多个角色包,然后用下一节的 SoD 规则检查组合是否危险。

### 职责分离(SoD):冲突对才是重点

SoD(Segregation of Duties)问的不是「权限多不多」,而是**危险组合**:

| 冲突对 | 风险故事 |
| --- | --- |
| 建/改 PO × 收货 | 虚订 + 虚收,配合体外存货 |
| 建/改 PO × 过发票 | 自己给自己定价格 |
| 收货 × 过发票 | 绕开三单匹配 |
| 过发票 × 执行付款 | 经典侵占路径 |
| 改供应商银行账号 × 付款 | 截留货款 |
| 销售订单 × 发货过账 | 货物流向体外 |
| 发货 × 开票 | 操纵收入确认时点 |

沙盘里勾选权限,矩阵会标 △(潜在冲突)与 ✗(当前用户已同时拥有)。真实项目用规则引擎扫全员;上线前与每季复核都应出一份**冲突用户名单**,冲突必须拆角色或加补偿控制(强制双人、抽检)。

### 审批流的边界与陷阱

审批解决「超权限的例外如何放行」,常见设计:

- **金额门槛**:5 千主管、5 万经理、50 万总监+财务……;
- **替补/代理**:休假时自动转交——要限制代理范围与时长;
- **紧急通道**:跳过审批的「加急」——必须留审计痕迹并事后复核,否则等于没审批。

记住:**审批人通过 ≠ 执行人可以无限做**。审批流批的是这一张单;权限仍限制他能不能改主数据、能不能自己过付款。

### 审计轨迹:事后还原每一次点击

内控事后靠三类痕迹:

1. **变更日志**:谁、何时、改了主数据/配置的哪个字段(旧值→新值);
2. **单据流**:这张发票参照哪张收货、哪张 PO、哪张申请——链条完整才能追责;
3. **过账凭证号与用户**:自动分录也带着触发它的业务用户或批处理作业名。

审计要问的不是「系统有没有日志开关」,而是**关键对象是否强制记录、日志是否防篡改、保留多久、谁有权查**。关掉变更日志「为了省空间」,等于主动拆除黑匣子。

### 给岗位打包:一个采购员角色示例

最小可用的「采购员」角色包大致包括:

- 显示与处理采购申请、建/改 PO(本公司代码 + 本采购组织);
- 显示供应商与信息记录(通常**不能**改银行账号——那是主数据专员或财务);
- 显示收货与发票状态(不能过账收货、不能执行付款);
- 显示本采购组的报表与例外。

显式**排除**:收货过账、发票校验过账、付款程序、供应商银行字段、过账期间开关。这样即使审批流配松了,SoD 仍有底线。

### 角色视角收束

到这里,三条角色线合龙:

- **管理层**(ROLE1)用驾驶舱问例外;
- **一线**(ROLE2)用单据走闭环;
- **权限与 SoD**(ROLE3)保证「能做的人」与「该做的人」一致,并且可审计。

流程教你会跑;角色教你会把系统交到对的人手上——后者往往决定上线后的第三个月,ERP 是公司神经中枢,还是一堆没人爱点的菜单。
