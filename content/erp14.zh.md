## 核心讲义

### MRP 的输入清单

MRP 是一次纯粹的计算,输入错则输出错。开跑前它要读五样东西:

1. **需求**:销售订单 + 剩余预测(独立需求),按日期分布;
2. **现有库存**:非限制库存(质检与冻结的不算!);
3. **在途供给**:未清采购订单、已下达生产工单——「已经在路上的,不要重复下」;
4. **BOM**:逐层展开的结构与用量;
5. **计划参数**:提前期、批量规则、安全库存——全部来自物料主数据(MD2 章的伏笔在此兑现)。

### 核心算法:净算 → 展开 → 偏置

**第一步:净算(netting)**。对每个物料、每个时间段:

```
净需求 = max(0, 毛需求 − 可用库存 − 在途供给 + 安全库存)
```

沙盘例:成品需求 200,库存 40 → 净需求 160。库存够就到此为止,这个分支不再往下炸。

**第二步:批量(lot sizing)**。净需求 160,下多大的单?

| 规则 | 结果 | 适用 |
| --- | --- | --- |
| 批对批(lot-for-lot) | 正好 160 | 贵重物料、定制件——零多余库存 |
| 固定批量 200 | 下 200,多 40 进库存 | 有起订量/整箱约束 |
| 定期批量(周期合并) | 合并两周需求一起下 | 订货成本高的物料 |

批量规则是「订货成本 vs 持有成本」的权衡——EOQ 的思想(INV2 章)在这里落地成配置。

**第三步:偏置(lead-time offsetting)**。需求日往前推提前期,得到**下单日**:

```
计划订单:160 台,完工日 = W5,提前期 1 周 → 下达日 = W4
```

**第四步:向下展开(explosion)**。上层计划订单变成下层毛需求:

```
车轮毛需求 = 160 × 2 = 320,需求日 = W4(父项的开工日!)
```

注意需求日是父项**开工**日而非完工日——车轮必须在组装开始时到位。然后对车轮重复净算→批量→偏置……逐层直到采购件,抛出**采购申请**。这个「低层码(low-level code)」顺序保证共用件(螺丝被 10 个产品用)只在最低层级汇总净算一次。

### 输出:建议与例外

MRP 的输出**全部是建议**,不是命令:

- **计划订单(planned order)**:建议生产,计划员确认后转生产工单;
- **采购申请**:建议采购,采购员转采购订单;
- **例外信息(exception messages)**:MRP 最有价值的输出——「提前期不足」「建议提前/推迟现有订单」「订单数量过剩」。计划员的日常不是看几万行计划,而是**处理例外清单**。

沙盘里把车轮提前期调到 4 周出现的红色警告,就是最经典的例外:**需求已经等不及正常提前期**。MRP 不会自作主张加急——它把矛盾亮出来,让人决策:加急(花钱)、分批(部分满足)、还是改交期(与客户谈)。

### 再生式 vs 净改变

全量重算(regenerative)每晚把所有物料算一遍,稳但慢;**净改变(net change)**只重算「有变动的物料」(新订单、收货、改 BOM 都会打标记),快但偶尔要全量校正。云时代内存计算让「随时全量」越来越普及,MRP 从「每晚一次」走向「准实时」。
